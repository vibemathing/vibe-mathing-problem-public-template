# Chapter 5: Suggestions, Validation & Cache

## Core Idea
The client normalizes different backend payloads into one `SearchResult` model, then projects each result into command-, term-, or tactic-specific `TryThis` suggestions. Tactic suggestions are tested against the current target without mutating the proof state.

## Frameworks Introduced
- **Normalize then project**
  - When to use: extending backend support or reasoning about suggestion behavior.
  - How: parse backend JSON into `SearchResult`; keep rendering logic independent of backend schema.
- **Speculative tactic validation**
  - When to use: a declaration might support several proof actions.
  - How: generate candidate tactics, parse and run each against a fresh metavariable under `withoutModifyingState`, keep candidates that do not throw.
- **Semantic cache key**
  - When to use: adding a parameter or backend.
  - How: include every request input capable of changing the response.

## Key Concepts
- **`SearchResult`**: normalized name plus optional type, documentation, URL, and kind.
- **Command suggestion**: `#check <name>` plus type/doc post-info.
- **Term suggestion**: the declaration name, optionally annotated with its type.
- **Tactic candidates**: `apply <name>`, `have : <type> := <name>`, `rw [<name>]`, `rw [← <name>]` when a type is available.
- **`checkTactic`**: runs a candidate on a fresh goal inside `withoutModifyingState` and returns `some goals.length` on successful execution, `none` on error.
- **Cache**: in-memory `IO.Ref` hash maps; separate caches for LeanSearch, StateSearch, and Loogle.

## Mental Models
- A backend result answers **what declaration might help**; projection answers **how it might be used here**.
- Local validation is a safety/quality filter over remote retrieval.
- `checkTactic` success means the tactic executed without an exception. The caller only checks `isSome`; remaining goal count is not required to be zero, so successful validation does not imply goal closure.

## Anti-patterns
- **Claiming validated means solved**: candidates may leave subgoals.
- **Mixing backend JSON parsing with Lean UI rendering**: normalization exists to keep those responsibilities separate.
- **Caching only by query string**: result count and, for StateSearch, revision change the response.
- **Mutating the user's proof while evaluating suggestions**: validation intentionally uses a fresh metavariable and `withoutModifyingState`.

## Reference Table
| Context | Projection |
|---|---|
| command | `#check name` |
| term | `name` |
| tactic | `apply` / typed `have` / `rw` / reverse `rw` |

| Backend | Cache key |
|---|---|
| LeanSearch | `(query, num_results)` |
| StateSearch | `(query, num_results, revision)` |
| Loogle | `(query, num_results)` |

## Failure Recovery
- Result lacks a type → no tactic candidates are generated by `toTacticSuggestions`; use declaration inspection.
- Candidate cannot parse or elaborate → drop it silently from tactic suggestions.
- StateSearch has no valid tactic group → display command-style declaration suggestions instead.
- Backend schema changes → diagnose in the backend-specific JSON parser before changing projection code.

## Key Takeaways
1. Normalize backend payloads before rendering suggestions.
2. Render differently for command, term, and tactic contexts.
3. Tactic validation is non-destructive and local.
4. Validation does not imply complete proof closure.
5. Cache keys must capture all response-shaping inputs.

## Implementation Decision Rule
When adding a new backend, first map its response into `SearchResult` rather than adding backend-specific rendering branches. Reuse the existing command/term/tactic projections when the semantics fit. Add a new cache dimension whenever a request parameter can change the returned set. If a new tactic projection is introduced, run it through the same non-destructive local validation boundary before exposing it as `TryThis`.
