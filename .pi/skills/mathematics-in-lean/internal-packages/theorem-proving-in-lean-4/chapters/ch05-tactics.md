# Chapter 5: Tactics

## Core Idea
Tactics are an interface for incrementally constructing proof terms. The useful discipline is to read each tactic as a controlled transformation of the current goal state and to keep subgoal creation, rewriting, simplification, and search local enough that the resulting proof remains understandable and robust.

## Frameworks Introduced
- **Backward goal transformation**
  - When to use: the desired proof term is easier to discover from the target than to write directly.
  - How: enter `by`, apply a tactic whose conclusion matches the goal, then solve the generated premises.
- **Exact-before-search**
  - When to use: a concrete term should close the goal.
  - How: prefer `exact term`; use `apply` when deliberately exposing premises is useful.
- **Context reshaping with `revert` / `generalize`**
  - When to use: induction or case analysis has hypotheses fixed too early or an expression should become an explicit variable.
  - How: `revert` dependencies back into the goal; `generalize h : t = x` when the relationship to the original term must be retained.
- **Local subgoal structure**
  - When to use: tactics generate several branches.
  - How: use case tags, indentation blocks, bullets, `focus`, or goal combinators so each tactic acts on the intended subgoal.
- **Targeted rewrite vs normalization**
  - When to use: equality information should change a goal.
  - How: use `rw` for a chosen replacement; use `simp` for repeated canonical simplification.
- **Combinator-controlled automation**
  - When to use: the same tactic should run across generated goals or alternatives.
  - How: sequence tactics, use `<;>`, `first`, `try`, `all_goals`, `any_goals`, and `focus` with explicit awareness of success/failure behavior.

## Key Concepts
- **Goal state**: local context plus target proposition/type.
- **`exact`**: close the goal with a term of the exact expected type.
- **`apply`**: match a theorem's conclusion to the goal and generate premises as subgoals.
- **`intro`**: introduce a function/quantifier input or assumption.
- **`assumption`**: close a goal from a matching local hypothesis.
- **`constructor`**: use the constructor of the target inductive proposition/data.
- **`cases`**: split a hypothesis/value by constructors.
- **`exists`**: provide existential witnesses.
- **`revert`**: move a local hypothesis and dependent items back into the target.
- **`generalize`**: replace an expression with a variable, optionally recording the defining equality.
- **Tactic combinator**: syntax controlling how tactics are sequenced across goals and failures.
- **`rw`**: rewrite by equations.
- **`simp`**: normalize using a simplification set.
- **`split`**: create branches corresponding to conditionals/matches.
- **Extensible tactic syntax**: Lean tactics can be extended with new syntax/macros; custom tactics should still expose clear goal transformations and kernel-checkable results.

## Mental Models
- Think of a tactic proof as a **proof-term program with an observable stack of obligations**. A good step reduces structural uncertainty.
- Use `exact` as a **commit point**: if the full intended term is known, let the expected type guide elaboration and close the goal.
- Use `apply` as a **premise generator** when the theorem to use is clear but its inputs still need proofs.
- Treat `revert` and `generalize` as **quantifier-shape tools**. They change what the later induction or case split is allowed to assume.
- Treat `simp` as a **rewrite engine with a database**, so reproducibility depends on what rules are active.

## Anti-patterns
- **Relying on autogenerated inaccessible names**: proof scripts become brittle when elaboration changes. Prefer structured case blocks or `rename_i` only when necessary.
- **Generalizing away a crucial relationship**: replacing an expression without recording an equality can make the new goal weaker in the wrong direction or unprovable.
- **`repeat (try t)` with a tactic that can succeed without progress**: this can loop forever.
- **Using `<;>` without understanding how many subgoals the left tactic produces**: later tactics may run in unintended branches.
- **Letting `simp` use a huge ambient rule set when a stable proof needs a small one**: use `simp only` or `rw`.
- **Using a tactic sequence as opaque search** when a short term proof states the reason directly.

## Code Examples
```lean
example (p q r : Prop) (hp : p) (hpq : p → q) (hqr : q → r) : r := by
  apply hqr
  apply hpq
  exact hp
```
- **What it demonstrates**: `apply` works backward from the target; `exact` closes the last concrete obligation.

```lean
example (p q : Prop) (h : p ∧ q) : q ∧ p := by
  cases h with
  | intro hp hq =>
      constructor
      · exact hq
      · exact hp
```
- **What it demonstrates**: branch structure mirrors constructors and keeps names local.

```lean
example (a b c : Nat) (h₁ : a = b) (h₂ : b = c) : a = c := by
  rw [h₁, h₂]
```
- **What it demonstrates**: direct rewriting when the desired substitutions are known.

```lean
example (n : Nat) : n + 0 = n := by
  simp
```
- **What it demonstrates**: simplification as canonical normalization.

## Reference Tables
### Core tactic choice
| Situation | Tactic | Resulting proof obligation |
|---|---|---|
| full term already known | `exact t` | none if `t` elaborates at target |
| theorem conclusion matches goal | `apply h` | theorem premises |
| implication / universal target | `intro` | body under new local assumption/variable |
| matching local fact exists | `assumption` | none |
| one-constructor target | `constructor` | constructor fields/premises |
| eliminate inductive value | `cases h` | one goal per possible constructor |
| existential target | `exists w` | predicate at witness `w` |
| impossible constructor combination | `contradiction` / constructor reasoning | closes inconsistent branch |

### Goal combinators
| Combinator | Decision rule |
|---|---|
| `t₁; t₂` | run `t₂` on all goals produced by `t₁` |
| `t₁ <;> t₂` | compact sequencing across generated goals |
| `first | t₁ | t₂` | choose first tactic that succeeds |
| `try t` | tolerate failure; ensure outer repetition still makes progress |
| `all_goals t` | require `t` on every current goal |
| `any_goals t` | apply where possible |
| `focus t` | isolate the first goal while running `t` |

### Rewrite controls
| Need | Form |
|---|---|
| reverse direction | `rw [← h]` |
| rewrite a hypothesis | `rw [h] at hx` |
| simplify target and context | `simp at *` with care |
| stable explicit rule set | `simp only [a, b, c]` |
| remove active simp rule | `simp [-lemma]` or local attribute control |
| conditional/match branching | `split` |

## Worked Example
Suppose induction on `n` produces an induction hypothesis that mentions a fixed `m`, but the recursive step needs the theorem for every `m`.

A repair workflow:
1. Before induction, `revert m`. The target becomes universally quantified over `m`.
2. Induct on the argument the definition recursively consumes.
3. In each branch, `intro m` again. The induction hypothesis is now polymorphic in `m` instead of frozen at the original value.
4. Apply the IH at the needed recursive-step argument.

If the issue is an expression rather than a variable, use `generalize h : complexTerm = x` so that the proof can case-split or induct on `x` while retaining an equation linking it to the original term. Omitting `h` is safe only if that relationship will never be needed.

## Failure Recovery
- `apply` creates an impossible premise → inspect the theorem's full type; perhaps a different theorem or an explicit argument is needed.
- `rw` does nothing → check direction and syntactic occurrence; simplify/unfold enough to expose the term, or move to `conv`.
- `simp` proves too much or changes too much → use `simp?` in an interactive environment if available, narrow to `simp only`, or replace with explicit rewrites.
- generated names cannot be referenced → structure the branch explicitly or use `rename_i`.
- induction/cases loses needed context → `revert` dependent hypotheses first.
- tactic composition loops → ensure repeated tactic failure/success correlates with genuine progress.

## Key Takeaways
1. Tactics remain proof-term construction; inspect the obligations they create.
2. `exact` is preferable when the complete proof term is available.
3. `revert` and `generalize` are central tools for repairing proof shape before induction/cases.
4. Structured subgoal blocks are more robust than scripts depending on incidental generated names.
5. `rw` communicates a selected substitution; `simp` communicates normalization.
6. Tactic combinators require explicit reasoning about success, failure, and goal multiplicity.
7. Mixing terms and tactics often produces clearer proofs than insisting on one style.
