# Chapter 7: Inductive Types

## Core Idea
An inductive declaration specifies exactly how values or proofs can be constructed; Lean generates recursors that specify how they can be consumed. Constructors, indices, and the generated eliminator should drive case analysis, recursion, and induction strategy.

## Frameworks Introduced
- **Constructor-first design**
  - When to use: defining a finite/recursive datatype or proposition.
  - How: enumerate the allowed constructors and their arguments; ensure recursive occurrences satisfy positivity constraints.
- **Recursor-first proof selection**
  - When to use: choosing between direct construction, `cases`, recursion, and induction.
  - How: inspect the generated recursor/motive and align the theorem with its major premise and minor premises.
- **Inductive propositions as proof objects**
  - When to use: a proposition is naturally characterized by finitely generated evidence.
  - How: declare constructors as proof rules; reason by cases/induction over proof evidence.
- **Index-preserving reasoning**
  - When to use: an inductive family such as vectors or equality has result indices constrained by constructors.
  - How: keep indices in the motive; use dependent elimination so impossible cases vanish and equalities survive.

## Key Concepts
- **Inductive type**: least type generated by declared constructors.
- **Constructor**: introduction form for an inductive type.
- **Recursor**: generated elimination/recursion/induction principle.
- **Motive**: family specifying the result type for each eliminated value.
- **Enumerated type**: inductive type with nullary constructors.
- **Recursive datatype**: inductive type whose constructors contain smaller values of the same type.
- **Inductive proposition**: inductive declaration living in `Prop`.
- **Subtype** `{x : α // p x}`: data value plus proof of a property.
- **Inductive family**: result type indexed by values that constructors may constrain.
- **Strict positivity**: restriction ensuring recursive occurrences appear in sound positions.
- **Singleton elimination**: limited exception allowing certain proposition eliminations to data despite general `Prop` restrictions.
- **Mutual inductive types**: several inductive types defined together when constructors refer across the group.
- **Nested inductive types**: recursive occurrence appears inside another strictly positive type constructor and is handled by Lean's inductive machinery when accepted.

## Mental Models
- Across constructors there is an **alternative**; inside one constructor its arguments are **all jointly available**. This mirrors disjunction vs conjunction.
- Use a recursor as the **public elimination interface** generated from the constructors.
- Induction is recursion whose motive lands in `Prop`: recursive constructor arguments receive induction hypotheses.
- For indexed families, a constructor encodes **both data and index equations**. Preserve those constraints instead of treating the index as independent.

## Anti-patterns
- **Inducting on a convenient variable rather than the argument the definition recursively consumes**: the IH may not match the recursive call.
- **Case-splitting a dependent value without accounting for context dependencies**: Lean may revert dependent hypotheses, or the proof may lose needed index information.
- **Assuming every `Prop` proof may be eliminated into arbitrary data**: proof irrelevance imposes elimination restrictions, with controlled exceptions.
- **Ignoring positivity/universe restrictions when inventing inductive declarations**: unsound/self-referential shapes are rejected for foundational reasons.

## Code Examples
```lean
inductive Color where
  | red
  | green
  | blue
  deriving Repr

#check Color.rec
```
- **What it demonstrates**: constructors generate an elimination principle.

```lean
inductive MyList (α : Type) where
  | nil : MyList α
  | cons : α → MyList α → MyList α

open MyList

def length : MyList α → Nat
  | nil => 0
  | cons _ xs => Nat.succ (length xs)
```
- **What it demonstrates**: recursive data and structural recursion over constructor subdata.

```lean
example (xs : List α) : xs ++ [] = xs := by
  induction xs with
  | nil => rfl
  | cons x xs ih =>
      simp [ih]
```
- **What it demonstrates**: induction follows the recursive structure and supplies an IH for the tail.

```lean
inductive Vec (α : Type) : Nat → Type where
  | nil : Vec α 0
  | cons : α → Vec α n → Vec α (n + 1)
```
- **What it demonstrates**: constructors constrain the index of an inductive family.

## Reference Tables
### Choose the eliminator
| Task | Mechanism | What you receive |
|---|---|---|
| build value/proof | constructor | constructor arguments become obligations |
| inspect finite alternative | `cases` / recursor | one branch per possible constructor |
| compute over recursive data | recursion / pattern match | results of recursive calls |
| prove recursive property | `induction` | induction hypotheses for recursive fields |
| prove constructor incompatibility | cases/`contradiction` | impossible branches close |
| derive equal constructor fields | `injection` | equalities between corresponding fields |

### Common inductive patterns
| Pattern | Representative shape | Operational use |
|---|---|---|
| optional value | `Option α` | represent partial results without inventing a default |
| product / sum | `Prod α β` / `Sum α β` | pair all components or choose one tagged alternative |
| inhabitation evidence | `Inhabited α` | carry a concrete default value usable in data-level computation |
| proof-only existence of a value | `Nonempty α` | state inhabitation in `Prop`; data extraction requires stronger evidence or choice |
| recursive sequence/tree | `List`, tree-like inductives | structural recursion and induction |
| mutual/nested family | constructors recurse across/inside accepted positive structures | inspect generated recursors; termination/positivity rules still govern recursion |

### Context dependency during cases
Before `cases h`, ask:
1. Do later local hypotheses have types depending on `h`?
2. Does the target depend on `h`?
3. Is `h` an arbitrary expression rather than a variable?
4. Do I need an equation tying the generalized value back to the original expression?

If yes, plan `revert`/`generalize` or use a dependent eliminator.

## Worked Example
Suppose a theorem about list append is stated as `∀ xs ys, (xs ++ ys).length = xs.length + ys.length`.
1. Inspect the definition of append: it recursively consumes the first list.
2. Induct on `xs`, not `ys`.
3. Base constructor `[]` reduces the equation directly.
4. `x :: xs` gives an IH for `xs`; simplifying append/length exposes exactly that IH.
5. If `ys` had been fixed in a way that made the IH too specific for the recursive step, revert it before induction.

The principle is broader than lists: choose the induction variable from the computation's recursive structure.

## Failure Recovery
- **IH does not match recursive term** → inspect which argument the definition recurses on; generalize dependent values.
- **`cases` creates ill-typed/lost hypotheses** → revert dependencies or use dependent matching.
- **Need to prove two constructor values unequal** → use constructor disjointness/case analysis rather than arithmetic reasoning.
- **Need equality of constructor fields** → use injection/congruence generated from constructor equality.
- **Indexed family has impossible cases** → strengthen motive and let dependent elimination use index constraints.

## Key Takeaways
1. Constructors define all legal inhabitants; recursors define the canonical ways to consume them.
2. Proof strategy should be derived from the inductive definition, not from superficial syntax.
3. Induction is most effective on the argument that actually drives recursion.
4. Indexed families encode invariants in result indices and require dependent reasoning that preserves them.
5. Case analysis may reshape dependent context automatically; inspect what was generalized/reintroduced.
6. Positivity, universes, and `Prop` elimination restrictions are foundational constraints, not arbitrary syntax rules.
7. Mutual and nested inductives extend the same constructor/recursor discipline; inspect generated eliminators rather than assuming an ordinary single-type induction scheme.
