# Chapter 3: AI for Discovering Mathematical Patterns

## Core Idea
AI-assisted discovery is most valuable when it turns an overwhelming search space into a small number of mathematically interpretable leads. The chapter develops two complementary routes: **learn hidden relations from mathematical data** and **search directly for improved algorithms**. In both, the operational endpoint is a precise, independently checkable mathematical artifact.

## Frameworks Introduced

### Supervised Discovery Pipeline: Prediction → Interpretation → Conjecture → Proof
- **When to use**: You have many objects with computed invariants/features and suspect a relation too high-dimensional for direct inspection.
- **How**:
  1. Build data with distinct roles: systematic/census samples, broad random/generalization samples, and deliberately constructed stress cases.
  2. Translate the question into a predictive task. The target should represent the mathematical quantity whose recoverability would imply a hidden relationship.
  3. Train a predictor and require genuine held-out accuracy.
  4. Use saliency/feature importance and ablation to identify which inputs carry the signal.
  5. Retrain on the reduced feature set. If performance survives, the candidate relation has become simpler and more interpretable.
  6. Combine the important features into natural domain quantities using mathematical knowledge.
  7. State a precise conjecture and stress-test it on constructed data outside model fitting.
  8. Use failures to add the missing variable or change the form of the conjecture; prove the surviving statement.
- **Why it works**: Prediction answers “is information present?” Interpretability asks “where is it?” Mathematics then asks “what invariant relation explains it?”

### TensorGame: Algorithm Search as Low-Rank Decomposition
- **When to use**: An algorithmic cost can be re-expressed as the rank/length of a decomposition of a structured mathematical object.
- **How**:
  1. Encode the computation as a tensor. For matrix multiplication, tensor entries identify which input products contribute to which output entries.
  2. Recognize that a rank-`R` tensor decomposition corresponds to an algorithm using `R` scalar multiplications.
  3. Cast decomposition as a one-player game: state = residual tensor; action = subtract a rank-one tensor; terminal state = zero residual.
  4. Reward short successful trajectories, since step count equals the multiplication count.
  5. Use a specialized policy/value architecture whose inductive bias respects tensor structure.
  6. Mix RL/self-play on the target with synthetic demonstrations generated by the easy inverse process (choose factors, then construct their tensor sum).
  7. Use basis changes and action normalization to enlarge effective exploration while eliminating redundant representations.
  8. Convert the discovered decomposition back into an explicit matrix-multiplication algorithm and verify it algebraically.
- **Why it works**: The formalization makes “find a faster algorithm” an exact search problem with a trustworthy terminal condition.

### AlphaEvolve-Style Program Evolution
- **When to use**: The candidate is naturally an executable program and an automatic evaluator can score correctness/performance.
- **How**:
  1. Start from a seed implementation and specify the evolvable region.
  2. Maintain a database/archive of good and diverse programs.
  3. Sample informative candidates and provide their code, performance, and task context to an LLM.
  4. Ask the LLM for code modifications, then compile/run them in a sandboxed evaluation pipeline.
  5. Use staged tests: inexpensive correctness/validity filters first, costly performance/full evaluation second.
  6. Insert successful/diverse variants into the archive and repeat.
  7. Once an algorithmic record appears, extract the mathematical idea and verify it independently of the evolution loop.
- **Why it works**: The LLM supplies broad program priors and mutation proposals; the evaluator converts open-ended generation into cumulative search.

## Key Concepts

### Knot-invariant discovery case
The motivating case relates geometric and algebraic knot invariants. Inputs include hyperbolic/geometric quantities such as volume, Chern–Simons information, cusp geometry (real/imaginary meridional and longitudinal translations), and injectivity radius. The target is the knot signature.

The study does not stop at prediction. Gradient/saliency analysis identifies a small subset of features. Domain interpretation combines cusp quantities into a **natural slope** based on the longitudinal/meridional relationship. A first conjectural formula is then attacked with purposely constructed knots; counterexamples expose the need for injectivity radius. The refined relation includes volume and an inverse power of injectivity radius and is then subjected to mathematical proof.

The transferable lesson is the *sequence of epistemic upgrades*:
**correlation → stable predictive signal → interpretable feature → natural mathematical quantity → conjecture → adversarial stress test → refined conjecture → proof**.

### Matrix multiplication as a tensor problem
For fixed block size `n`, matrix multiplication can be encoded by a sparse tensor `T_n`. A rank-one term is a product of one linear form in entries of `A`, one linear form in entries of `B`, and a contribution to entries of `C`. A rank-`R` decomposition therefore yields `R` scalar multiplications. Recursively applying a base algorithm gives asymptotic cost approximately `O(N^(log_n R))`, which makes each rank improvement mathematically meaningful.

### Specialized search versus meta-search
- **AlphaTensor** searches directly in a carefully designed mathematical solution space. It is highly targeted and sample-efficient once the game/architecture exists.
- **AlphaEvolve** searches the meta-space of programs/heuristics. It is more general and can accumulate ideas, yet it depends heavily on evaluator quality and may spend more compute per candidate.

A useful combined strategy is **broad program-level exploration → specialized/exact search or formal check → mathematical interpretation → feed newly discovered structure back into representation/evaluator**.

## Mental Models

### Predictor as Microscope
A predictive model is useful when it reveals variables humans should inspect. Its role resembles an instrument that makes hidden structure visible; the mathematical theory comes from explaining and validating the signal.

### Stress Data as an Adversary
Constructed examples are not merely another test set. Design them to attack the proposed relation's suspected weak points. A counterexample is information about which term/assumption is missing.

### Search Representation Determines Discoverability
If equivalent mathematical objects appear as many unrelated encodings, the algorithm wastes effort. Symmetry-aware normalization, basis changes, and mathematically meaningful actions can radically reshape the effective search space.

### Evaluator as Fitness Landscape
In program evolution, the evaluator defines what evolution can see. A biased, incomplete, or gameable evaluator creates a distorted landscape; adding model intelligence cannot repair an incorrect objective.

## Anti-patterns
- **Accuracy-to-theorem leap**: promoting a predictive relationship directly to a theorem.
- **Interpretability after leakage**: explaining a model whose test data or constructed stress cases influenced training.
- **Feature importance without stability checks**: relying on one run/seed when the selected features are not reproducible.
- **Generic architecture on a structured tensor/game**: ignoring known invariances and paying for the lost inductive bias with huge search cost.
- **Evaluator gaming**: accepting a program because it wins a benchmark while violating hidden correctness or generality assumptions.
- **Single-best archive**: keeping only the top program and destroying diversity needed for future innovation.

## Reference Tables

### Discovery route selector
| Mathematical situation | Route | Key validator |
|---|---|---|
| relation among computed invariants | supervised + interpretability | held-out/stress data, then proof |
| decomposition with exact residual | object-level RL/TensorGame | exact zero residual + algebraic identity |
| algorithm encoded as executable code | program evolution | correctness suite + performance evaluator |
| route unclear but evaluator strong | start broad with program/meta-search | evaluator integrity; then specialize |

### Data roles in conjecture discovery
| Dataset | Purpose | Do not use for |
|---|---|---|
| Census/systematic | broad known coverage | claiming out-of-distribution robustness |
| Random/generic | distributional generalization | hand-picking only easy families |
| Constructed/adversarial | boundary attack/counterexample search | routine training that leaks the stress test |

## Worked Example
A researcher wants a lower multiplication count for a fixed matrix size.

**Route A — object-level**:
1. derive the matrix-multiplication tensor;
2. define each move as a rank-one factor subtraction;
3. train/search until the residual is exactly zero;
4. count the terms;
5. reconstruct the bilinear algorithm and symbolically verify every output entry.

**Route B — program-level**:
1. write a baseline construction/search program;
2. create an evaluator that rejects invalid algorithms and measures multiplication count/runtime;
3. evolve modifications while maintaining a diverse archive;
4. when a lower-count candidate appears, extract its algebraic identities and verify outside the program.

Choose Route A when the tensor game is manageable and a specialized search can exploit its symmetry. Choose Route B when the useful innovation may occur in heuristic/search code or when the program representation generalizes to multiple problems.

## Key Takeaways
1. Make discovery pipelines end in a precise object or statement that can survive independent checking.
2. Separate data used for fitting from data designed to attack a conjecture.
3. Interpretability earns value when it reduces a high-dimensional prediction to a mathematically natural relation.
4. Recasting algorithm design as exact search can expose reward/terminal signals unavailable to natural-language generation.
5. Specialized RL and LLM-guided program evolution solve different search problems and can be composed.
6. Diversity, symmetries, synthetic demonstrations, and trustworthy evaluators are engineering choices with mathematical consequences.
