# 05 — Dependent Types and Term Construction

## Core Idea

Tactics become predictable when you know the term they are trying to build. This chapter is the semantic layer: functions, inductive types, structures, logical constructors, equality, quantifiers, and typeclass-driven notation.

## Judgments and universes

`a : A` states that term `a` has type `A`.

Lean stratifies types using universes:

- propositions live in `Prop` (`Sort 0`);
- ordinary data types commonly live in `Type` (`Type 0`, i.e. `Sort 1`);
- higher universes prevent a single self-containing universe.

The exact universe arithmetic rarely matters in everyday proofs, but universe-polymorphic declarations explain types such as `Sort u` and errors involving incompatible levels.

## Simple and dependent functions

### Simple function

Given `A` and `B`, a term of `A → B` consumes an `A` and returns a `B`.

```lean
fun x : A => body
```

### Dependent function

In a dependent function, the result type may depend on the input. Universal quantification is the proposition-valued instance of this pattern.

A key declaration rule: a parameter's type can refer only to terms that are already in scope. If a later type depends on `x`, declare `x` first.

### Currying

Multiple arguments are nested single-argument functions. Read:

```lean
A → B → C
```

as `A → (B → C)`. This explains why `intro` removes the leftmost binder and why `apply` can create several argument goals.

## Function terms as reusable constructions

Function application and composition are ordinary terms. When a tactic step seems magical, try to express it as:

```lean
f argument
```

or as a lambda. This often exposes the required premise immediately.

## Inductive types

An inductive type is generated by its constructors. To build a term, choose a constructor and provide its arguments. To consume a term, consider which constructor created it.

### Recursion vs cases vs induction

- `match` / `cases`: distinguish constructor forms;
- recursive definition: produce data by recursively processing constructor arguments;
- induction/recursor: prove a family of propositions with hypotheses for recursive pieces.

If plain cases leave you without the fact needed for recursive subdata, use induction.

### Empty/inhabited caution

A type can have no constructors (hence no terms). A constructor can also be recursively self-demanding in a way that yields no finite inhabitant. Do not invent witnesses merely because a type name exists.

## Structures

A structure is a single-constructor inductive type with named fields. Operationally:

- construct it with its constructor or `⟨field₁, field₂, ...⟩`;
- consume it through projections `obj.field` or pattern matching.

Dependencies between fields are allowed. This matters for existential-like and mathematical structures where later evidence depends on an earlier witness.

## Propositional constructors

### `And`

Think of `P ∧ Q` as a two-field proof structure. To construct it, provide proofs of both sides. To consume it, project/destructure those proofs.

### `Or`

`P ∨ Q` has two constructors: one carries a proof of `P`, the other a proof of `Q`. Construct by choosing one. Eliminate by handling both.

### `Iff`

`P ↔ Q` packages two functions, `P → Q` and `Q → P`. A proof usually constructs both directions.

### `Not`

`¬P` reduces to `P → False`. This explains `intro` for a negation target and function application for using a negated hypothesis.

### Classical logic

Some propositions require classical principles. In an intended classical development, Lean's classical namespace/instances can supply excluded-middle/choice consequences. Keep this dependency visible when constructive content matters.

## Equality

Equality is an inductive proposition whose fundamental constructor is reflexivity. `rfl` succeeds when the target is reducible to a reflexive relation supported by the relevant reflexivity theorem.

For non-definitional equality:

- use known equalities with `rw`;
- use transitivity (`calc`, `Eq.trans`, etc.);
- use congruence when applying functions to equal inputs.

Failure of `rfl` often means two mathematically equal expressions are not definitionally identical and need a theorem/normalization step.

## Quantifiers

### Universal quantifier

`∀ x, P x` behaves like a dependent function type. To prove it, return a proof for arbitrary `x`; to use it, apply it to a concrete term.

### Existential quantifier

`∃ x, P x` packages:

1. a witness `x`;
2. a proof of `P x`.

Construction and elimination preserve dependency: after extracting `x`, the proof's type refers to that exact witness.

## Typeclasses and overloaded notation

Surface notation frequently calls a class method. For multiplication, the expression may elaborate through a heterogeneous multiplication class, then an instance for the concrete type, then the underlying operation.

### Diagnostic procedure

1. `#check` the expression.
2. If surface notation hides the mechanism, inspect its underlying declaration via Ctrl-click/source.
3. Temporarily request explicit pretty printing when useful.
4. Identify the required class and concrete instance.
5. Inspect/infer the instance chain (`#check`, `infer_instance`, source search).
6. Add assumptions only when the missing structure is genuinely required by the theorem.

This prevents treating an instance-synthesis failure as a theorem-proving failure.

## Constructor/eliminator table

| Type shape | Construction | Elimination/use |
|---|---|---|
| `A → B` | `fun a => ...` | apply function to `a` |
| `∀ x, P x` | dependent lambda | instantiate with term |
| structure | constructor / tuple | projections / match |
| inductive sum-like | choose constructor | cases/match all constructors |
| `P ∧ Q` | pair of proofs | projections/destructure |
| `P ∨ Q` | left/right constructor | case split |
| `∃ x, P x` | witness + proof | extract witness + proof |
| `x = x` | reflexivity | rewrite/substitute |

## Worked Example — construct and consume conjunctions

Given `h : P ∧ Q`, the target `Q ∧ P` is a one-constructor object with two fields. Destructure or project `h` to obtain proofs of `P` and `Q`, then invoke the conjunction constructor with the fields reversed. This same build/consume pattern generalizes to structures: inspect the constructor fields to build a value; inspect projections or pattern-match to use one.

## Failure modes

- **Constructor doesn't fit target:** inspect the fully elaborated target type.
- **Dependent field mismatch:** ensure later evidence is built for the exact earlier witness.
- **Universe error:** check whether a declaration unnecessarily fixes `Type` instead of a polymorphic universe.
- **Instance error:** trace structure assumptions before adding arbitrary imports/instances.
- **Nested term proof unreadable:** switch locally to tactic construction while preserving the same constructor logic.

## Key Takeaways

Every proof step has a term-level meaning. Learn the constructors and dependent-function structure, and tactic routing becomes a mechanical consequence of the goal's type.
