# Chapter 6: Definition, API, and Library Engineering

## Core Idea

A mathematical definition creates downstream cost. A good formal library therefore treats the definition as the beginning of an interface: basic theorems, extensionality, coercions, typeclass instances, canonical simplification rules, and representative client proofs must be designed together.

## Definition Engineering Checklist

For a new object, answer:

1. **Purpose:** which downstream theorems/operations must be easy?
2. **Generality:** which assumptions are genuinely required?
3. **Construction:** what data/axioms define the object?
4. **Observation:** how do users inspect or compare objects?
5. **Coercions:** which canonical maps should Lean insert automatically?
6. **Instances:** which algebraic/order/topological structures should be inferred?
7. **Canonicalization:** what normal forms should `simp` target?
8. **Characterization:** which iff/extensionality/universal-property lemmas capture the concept?
9. **Clients:** can several realistic proofs use the API without unfolding the representation?

### Minimal axioms, immediate API

There is a trade-off between primitive structure fields and derived theorems. Fewer primitive axioms can make instance construction easier to reason about and reduce redundancy, but users should receive the expected symmetric laws immediately as proven API. The group examples in the source illustrate deriving right-side unit/inverse laws from a smaller axiom set and then marking the right stable identities for simplification.

### Generality with ergonomics

Prove a theorem under the weakest useful algebraic assumptions when this creates real reuse. A linter or manual review can detect unused structure. Keep specialized wrappers when they improve inference, names, or discoverability. “Maximum generality” is not a license to make the user interface unreadable.

## Coercions and Typeclasses

Invisible maps are valuable when they model mathematically canonical forgetful/embedding operations. When users repeatedly fight casts or instance search:

1. inspect the inferred type and instance;
2. make one conversion explicit to diagnose the path;
3. search for the canonical map already in the library;
4. if the same friction recurs, repair the API rather than patching every proof.

Formalization can expose a mathematical hierarchy more cleanly than informal notation, where many forgetful maps are silently suppressed.

## Generated/Closed Objects

Top-down definitions can leverage existing lattice infrastructure. For example, define “the smallest closed/subobject generated by `S`” as an intersection/infimum of all closed objects containing `S`; then prove closure-operator laws and inherit general complete-lattice results. This can be more reusable than constructing the object element by element.

## Gold-Standard Definitions

For shared infrastructure such as mathlib, “mathematically equivalent” is insufficient by itself. The definition should:

- sit at the right point in the hierarchy;
- compose with existing abstractions;
- avoid unnecessary implementation commitments;
- have a stable, idiomatic API;
- be reviewed by both domain and Lean experts;
- support theorems users actually want.

This is why AI-generated definitions demand heavier review than AI-generated proofs: the kernel can reject an invalid proof, but it cannot know that a compiling definition omitted a mathematical axiom or chose a damaging abstraction.

## Anti-patterns

- Repeatedly unfolding structures in client proofs.
- Adding broad coercions that create ambiguity.
- Marking every true equation as a simp lemma.
- Building theory in isolation from a target that demonstrates usability.
- Upstreaming a technically correct AI definition before semantic/API review.

## Validation Checkpoint

Treat downstream client proofs as API tests. Create at least two representative uses: one routine theorem that should be short and one boundary case that stresses coercions, extensionality, or instances. If both require repeated unfolding, manual casts, or implementation-specific facts, the API is incomplete. Check whether a characterization theorem, extensionality lemma, simp rule, constructor, or instance removes the repetition. Also inspect generality: the core definition should support foreseeable reuse, while convenience wrappers should preserve ergonomics for common concrete cases.

## Key Takeaways

Definitions, theorem statements, and APIs form one engineering unit. Optimize for downstream mathematical operations and stable abstraction boundaries, then let real client proofs test the design.
