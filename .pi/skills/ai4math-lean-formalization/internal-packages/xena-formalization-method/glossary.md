# Glossary

**API** — The public constructors, eliminators, lemmas, coercions, instances, extensionality results, and simplification rules through which users work with a definition. See Ch. 6.

**Autoformalization** — Translating informal mathematical text into a formal language, including statements, definitions, or proofs. Statements/definitions require semantic audit even when they compile. Ch. 12.

**Blueprint** — A dependency-oriented human document for a large formalization, cross-linked to code and updated as the proof is understood. Ch. 10.

**Canonical isomorphism** — An isomorphism supported by additional uniqueness/naturality/structural properties. It is not unrestricted equality; prove compatibility with the operations used. Ch. 4.

**Choice / Prop-to-data boundary** — Moving from “there exists an object” to selected data may use classical choice and can destroy executability. Ch. 7.

**Coercion** — A canonical conversion Lean may insert automatically. Good coercions express a stable mathematical hierarchy; bad/ambiguous ones obscure types. Ch. 6.

**Definitional equality** — Equality by computation/reduction of terms. Important for `rfl`, `change`, and elaboration, but sensitive to implementation choices. Ch. 4.

**de Bruijn factor** — Informal measure comparing formal proof/code size with human exposition. It varies heavily with prerequisite library maturity.

**Eliminator / recursor** — Principle generated by an inductive type for consuming its values. Into `Prop` it appears as induction; into data it appears as recursion. Ch. 5.

**Extensionality** — A theorem reducing equality of structured objects to equality of observable components/behavior. Ch. 4.

**Filter** — A generalized notion of “eventually/large enough” sets used to unify limits, neighborhoods, continuity, and convergence. Ch. 9.

**Gold-standard definition** — A shared-library definition whose semantics, generality, hierarchy placement, API, and maintainability have received expert review. Ch. 6/12.

**Kernel** — Lean's small trusted type checker. Tactics can be untrusted proof generators because the kernel rechecks resulting proof terms. Ch. 8.

**Mathematical typo** — A locally repairable omission/imprecision in informal mathematics that preserves the conceptual argument after correction. Distinguish it from a structural failure. Ch. 10.

**Misformalization** — Formal code that encodes the wrong claim/concept: low-level typo, missing hypothesis, quantifier error, definition mismatch, or high-level misunderstanding. Ch. 12.

**Normalization** — Transforming an expression toward a canonical form so rewriting or a domain solver can work predictably. Ch. 3/4.

**Principal filter** — A filter generated by an ordinary set, useful as the concrete bridge for understanding general filters. Ch. 9.

**Proof certificate** — Machine-checkable evidence from a computation/search that a small trusted checker can validate. Ch. 8.

**Proof state** — Current local hypotheses plus target shown by an interactive prover. Use it as active reasoning feedback. Ch. 2.

**Propositional equality** — An explicit proof of `a = b`, distinct from definitional equality. It supports substitution/rewriting. Ch. 4.

**Quotient lift** — Construction of a function out of a quotient from a function on representatives plus a proof that it is invariant under the equivalence relation. Ch. 5.

**Reflection** — Automation that reifies a goal into a computable syntax, normalizes/decides it, and uses a proved correctness theorem to produce a kernel-checkable proof. Ch. 8.

**Representation bridge** — A proved conversion/equivalence, plus compatibility lemmas, connecting two models used for different proof or computation tasks. Ch. 7.

**Simp normal form** — The intended direction toward which simplification lemmas reduce expressions. A coherent orientation helps termination and predictability. Ch. 4/6.

**Statement semantics audit** — Human mathematical check that a formal theorem matches the intended informal claim. This is separate from proof checking. Ch. 1/12.

**Subsingleton** — A type in which all terms are propositionally equal. Uniqueness does not imply definitional identity. Ch. 4/7.

**Tendsto** — Filter-based relation expressing that a function maps one notion of eventuality/convergence into another; unifies many limit/continuity statements. Ch. 9.

**Totalization** — Defining an operation on every input even when ordinary mathematics treats it as partial; intended theorems then carry domain hypotheses. Ch. 7.

**Universal property** — A specification characterizing an object via maps and uniqueness. Powerful for stable APIs, especially maps out of quotients/tensors/localizations, but may not expose all element-level facts. Ch. 5/7.
