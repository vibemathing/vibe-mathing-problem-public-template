# Lakatos: Proofs and Refutations

**Source**: *Proofs and Refutations: The Logic of Mathematical Discovery* / 《证明与反驳：数学发现的逻辑》, Imre Lakatos. Chinese EPUB supplied by the user; translated by 方刚、兰钊. 2 chapters + 2 methodological appendices, with historical footnotes.

## Use This Skill When

Use this skill when a task involves a conjecture, proof, counterexample, evolving definition, theorem restriction, competing proofs, or a formalization whose relationship to the original problem is uncertain. It is especially useful when the user asks how a failed proof should change the theorem, which assumption a counterexample exposes, whether a restriction is ad hoc, or how to recover the discovery logic hidden by a polished textbook presentation.

Do not invoke it for routine calculation, direct retrieval of a known theorem, or mechanical proof checking inside a fixed formal system unless the user also wants methodological diagnosis of assumptions, translation, scope, or concept formation.

## Minimum Working Context

Extract or infer, without inventing missing facts:

- **C** — current conjecture or claim.
- **P** — proof idea, decomposed into explicit lemmas `L1...Ln` when possible.
- **R** — refutation/counterexample candidates.
- **D** — current definitions and domain restrictions.
- **G** — user's goal: certainty, breadth, explanatory depth, discovery, teaching, or formalization.

If some items are unavailable, proceed with a provisional analysis and label what remains underdetermined.

## Orientation: Route the Task

1. **A counterexample exists** → run **Counterexample Triage**.
2. **The conclusion fails but every stated lemma survives** → run **Hidden-Lemma Search**.
3. **A lemma fails but the main conjecture survives** → run **Rule 4 / Proof Deepening**.
4. **A repair depends on redefining terms or excluding examples** → run **Definition & Domain Audit**.
5. **Several proofs support “the same” conjecture** → run **Proof-Content Comparison**.
6. **The argument is translated into algebra, logic, code, a model, or a formal system** → run **Translation-Procedure Audit**.
7. **A textbook result looks arbitrary or magical** → run **Heuristic Reconstruction**.

## Core Framework: Proofs and Refutations

Treat an informal proof as a **decomposition of a conjecture into sub-conjectures (lemmas)** whose interaction can be criticized. A proof can remain heuristically valuable even when the original conjecture fails.

### Rule 1 — Prove and Refute Together

Given a conjecture, attempt a proof and search for counterexamples in parallel. Turn the proof into a list of non-trivial lemmas. Search both for:

- **global counterexamples**: refute the main conjecture;
- **local counterexamples**: refute a proof lemma.

### Counterexample Triage

| Global? | Local? | Diagnosis | Next move |
|---|---|---|---|
| yes | yes | conjecture and identified lemma fail | **Rule 2**: incorporate the relevant lemma as a condition, then retest |
| yes | no | proof analysis is incomplete | **Hidden-Lemma Search**; restore falsity transfer |
| no | yes | proof is weaker than the conjecture | **Rule 4**: replace the failed lemma; consider a deeper proof |
| no | no | may still expose poor scope/explanation | treat as a **heuristic counterexample**; try **Rule 5** |

### Rule 2 — Lemma Incorporation

When a global counterexample appears, identify a proof lemma that it falsifies. Make that lemma explicit and incorporate the corresponding condition into the improved conjecture. Prefer a condition generated by the proof architecture over an unrelated “safe” restriction.

**Falsity-transfer check**: a mature proof analysis should make a global counterexample falsify some relevant lemma. If the conclusion fails while all listed lemmas remain intact, assume the decomposition is incomplete and search for a hidden lemma.

### Rule 3 — Escalate Local Counterexamples

For each local counterexample, test whether it is also global. If yes, apply Rule 2. If no, do not waste it: it can reveal a need for a stronger lemma or a deeper proof.

### Rule 4 — Repair Local-Only Failure

If a local counterexample refutes a lemma while the main conjecture survives, replace the false lemma with an unfalsified, more adequate lemma.

- **Weak mode**: repair the lemma inside the current proof idea.
- **Radical mode**: invent a deeper proof whose range includes cases excluded by the current proof.

Use radical mode when repeated patches keep narrowing the theorem, or when alternative proofs expose different explanatory structures.

### Rule 5 — Deductive Guessing

Given any counterexample, seek a deeper theorem generated from a proof/construction that explains why the former counterexample no longer functions as one. Use the structure of the problem and proof to generate the next conjecture; do not depend only on inductive pattern-fitting over examples.

## Definition & Domain Audit

When a repair changes definitions or scope, classify it before accepting it:

- **Monster-barring (怪物排除法)** — reject the counterexample by redefining the object so it no longer counts. Flag when the redefinition mainly protects the theorem and bypasses the proof.
- **Exception-barring (例外排除法)** — add restrictions that carve out a safe domain. Ask whether each restriction is motivated by a proof dependency; unrelated conditions are fragile and may throw away valid cases.
- **Monster-adjusting (怪物校正法)** — reinterpret the counterexample so its measurements or structure conform to the theorem. Require an independent reason for the reinterpretation.
- **Concept stretching (概念拉伸)** — deliberately broaden a concept so previously excluded objects become legitimate tests. Use it to expose hidden limitations, then control it so arbitrary semantic distortion does not replace criticism.
- **Proof-generated concept (证明引生概念)** — prefer concepts extracted from what a successful/deep proof actually needs. Track which proof operation or lemma generated the concept.

## Proof-Content Comparison

Two proofs of an initially identical conjecture can yield different improved theorems because they expose different lemmas, conditions, and domains. Compare proofs on:

1. **scope** — which cases the proof handles;
2. **depth** — whether it explains a wider family of phenomena;
3. **counterexample productivity** — which failures it makes visible;
4. **concept productivity** — which useful definitions/classes it generates;
5. **repair path** — whether failures suggest local patching or a new theory.

Do not optimize only for certainty. A proof may be rigorous yet explanatorily shallow or domain-poor.

## Translation-Procedure Audit

When informal mathematics is translated into vector algebra, logic, software, a model, or another “dominant theory”:

1. List source concepts and their translated counterparts.
2. For each translation, decide whether it claims **meaning preservation** or merely **stipulates a new meaning/abbreviation**.
3. If meaning preservation is claimed, treat the translation as fallible: identify aspects that may be lost, added, or split.
4. If new meaning is stipulated, check whether the original problem has silently been replaced.
5. Separate certainty **inside** the target formal system from uncertainty in axioms, modeling, definitions, and translation.
6. If the formal proof checks but the application fails, audit the translation/model boundary before attacking deduction.

## Heuristic Reconstruction

For a polished theorem, definition, or textbook proof that feels unmotivated, reconstruct:

`problem → naive conjecture → proof idea → exposed lemmas → counterexample/failure → hidden assumption → revised theorem → proof-generated concept → new problem`

Use this especially for teaching, explanation, design review, or research retrospectives. The appendices show uniform convergence, bounded variation, Riemann integration, and Carathéodory measurability as examples of definitions becoming intelligible when reattached to their proof-ancestors.

## Failure Recovery

- **No proof decomposition available** → infer a provisional lemma graph from the transformations in the argument; mark inferred lemmas.
- **Several hidden lemmas fit the same failure** → design discriminating counterexamples that falsify one candidate while preserving others.
- **Every fix shrinks the domain** → switch from exception-barring to Rule 4 radical mode or Rule 5.
- **Definitions keep moving** → record a definition genealogy and test whether changes track proof needs or merely protect the claim.
- **A formal proof passes but reality/example fails** → inspect translation, model assumptions, and the chosen dominant theory.
- **Counterexample status depends on terminology** → report both interpretations and identify which term must be stabilized for the next test.
- **Evidence is insufficient** → return “insufficient to choose among these repair paths” and name the smallest next proof step or counterexample that would discriminate them.

## Output Contract

For a substantive analysis, produce:

1. **Current claim and proof map** — conjecture, explicit lemmas, inferred hidden lemmas.
2. **Counterexample classification** — global/local/heuristic and why.
3. **Method diagnosis** — which Lakatosian move is occurring or should occur.
4. **Revised claim/proof** — condition incorporation, lemma replacement, deeper proof route, or translation repair.
5. **Next tests** — counterexamples chosen to distinguish competing diagnoses.
6. **Scope warning** — what the revised result still does not establish.

## SELF_CHECK

Before finishing, verify:

- Did I distinguish failure of the theorem from failure of its proof?
- Did every new restriction come from an identified proof dependency, or did I label it as a provisional engineering choice?
- If a global counterexample survives all listed lemmas, did I search for hidden lemmas?
- Did I test local counterexamples for global status?
- Did I consider a deeper proof before accepting repeated domain shrinkage?
- Did I track definition changes and possible monster-barring/adjusting?
- If formalization is involved, did I separate formal validity from translation/model fidelity?
- Did I preserve uncertainty where the source method gives no final guarantee?

## Scope & Limits

This skill operationalizes the methodological content of the supplied book. It does not guarantee discovery of a final theorem, a unique hidden lemma, or a once-for-all definition. It preserves the book's central fallibilist stance: criticism can improve conjectures, proofs, and concepts while leaving new problems open. Formal proof checking may be decisive relative to a fixed formal system; application still depends on axioms, translation, and modeling choices.
